# tools/sandbox — microVM sandbox for autonomous agents

- Autonomous agents run inside one Apple `container` microVM per mission (per-mission
  granularity): `spawn.py up` starts `container run -d --name mission-<feature> -v <repo>:/work -w /work botfiles-agent sleep infinity`, and each agent attaches via `container exec -it -e ORBAL_NET_* -w /work mission-<feature> <harness cmd>`. herdr's PTY (banner match + send-keys) works unchanged; coordination is the host orbal-net server the guest reaches with the `orbal-net` CLI over TCP (ORBAL_NET_URL/TOKEN/AGENT injected per exec). <source: orchestration/spawn.py sandbox_wrap/mission_up, 2026-07-08>
- Backend is Apple `container` (Virtualization.framework, one lightweight Linux VM per container), native to macOS 26 / Apple Silicon. Install + boot + image build: `bash sandbox/build.sh` (idempotent; runs `brew install container` and `container system start --enable-kernel-install` as needed). <source: sandbox/build.sh, 2026-07-07>
- Image `botfiles-agent` (sandbox/Containerfile): debian-slim + git/python3/node + the harnesses via npm; a builder stage runs `cargo install orbal-net` (registry, git fallback until v0.1.0 ships) and copies the binary to `/usr/local/bin/orbal-net`; bakes AGENTS.md and reuses `provision.sh` at build to wire each harness config. Rebuild after editing AGENTS.md or bumping the pinned orbal-net version. <source: sandbox/Containerfile, 2026-07-08>
- Isolation boundary: guest sees only `/work` (the mission's own working copy, writable) + outbound NAT network; host `$HOME`, SSH keys, other repos, and `/etc` are NOT in the guest (kernel-level VM boundary). Verified: guest `ls /Users` fails. <source: container run probe, 2026-07-07>
- Multiple missions on one repo don't clobber each other: `mission_workdir()` gives each mission a self-contained local git clone (hardlinked objects, cheap) mounted at `/work` on branch `mission-<feature>`. A bare `git worktree` can't be mounted alone (its `.git` points outside the mount, so git breaks in the guest — verified). `mission_down` runs `harvest()` = `git -C <repo> fetch <clone> +mission-<feature>:mission-<feature>` to bring commits back before deleting the clone; if harvest fails the clone is kept so work is never lost. Agents commit locally in-VM (origin isn't mounted, so no in-VM push); only committed state is cloned. A non-git repo falls back to a direct shared mount. Verified: two missions on one repo stayed isolated and both branches harvested back. <source: orchestration/spawn.py mission_workdir/harvest, 2026-07-08>
- Credentials: harnesses authenticate from their own stores, not env vars. `mission_secrets()` exports the claude Keychain OAuth cred to `claude.credentials.json` and copies `~/.codex/auth.json` into a per-mission `/tmp/botfile-secrets/<feature>` mounted read-only at `/secrets`; the entrypoint copies them into the guest HOME. The sandbox necessarily holds a copy of the creds so agents can call the model APIs (same trust as running the harness on the host); the secret is never printed. <source: orchestration/spawn.py mission_secrets + sandbox/entrypoint.sh, 2026-07-07>
- Vercel/eve missions: `mission_secrets()` also proxies the host `vercel login` cred (`~/Library/Application Support/com.vercel.cli/auth.json` -> per-mission `vercel.auth.json`), which the entrypoint drops at the guest `~/.local/share/com.vercel.cli/auth.json`, and the image bakes the `vercel` CLI (npm global). So an in-VM agent's `vercel deploy` authenticates as the host account with zero manual key setup (verified: guest `vercel whoami` returns the host's team; AI Gateway model calls then resolve via OIDC). Keep this provisioning for any eve/Vercel role or deploys break. Caveat: eve requires Node >=24 but the image bakes Node 22 - agents worked around it by installing Node 24 in-VM; bake Node 24 before the next eve mission. <source: eve-harness-impl mission - orchestration/spawn.py mission_secrets + sandbox/entrypoint.sh + sandbox/Containerfile, 2026-07-09>
- Default ON; `BOTFILE_NO_SANDBOX=1 python3 spawn.py up ...` runs bare on the host (debugging only). `spawn.py down <feature>` stops the VM and wipes its secrets dir. <source: orchestration/spawn.py, 2026-07-07>
- Not covered (documented, not silent): outbound egress is open NAT (any host reachable); all agents in one mission share the VM (per the chosen granularity). Add an egress allowlist / per-agent VMs later if the threat model tightens. <source: design decision, 2026-07-07>
